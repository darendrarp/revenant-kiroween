# How Kiro was used — REVENANT (honest write-up)

> This document is the full, honest account of Kiro usage in this project. It is
> written for the Kiroween 2026 judges and for anyone continuing the project.
> Nothing here is embellished: what Kiro did, what the builder did by hand
> following Kiro's documented workflow, and what could not be done are all
> stated plainly.

## TL;DR

- ✅ **Spec-driven development, for real.** Requirements (EARS), design, and
  tasks were written in `.kiro/specs/revenant/` **before** any code, and the
  build followed the task list in order. The spec changed twice during the
  build (parallel lookups; timeline via availability anchors, not CDX), and
  both changes are recorded in the design decision log.
- ✅ **Steering docs** (`.kiro/steering/product.md`, `tech.md`,
  `structure.md`) + root `AGENTS.md` capture the product, stack, constraints,
  and rules, so any Kiro session starts with full context.
- ✅ **Agent hooks** (`.kiro/hooks/*.json`, schema `v1` per
  [kiro.dev/docs/hooks](https://kiro.dev/docs/hooks/)): run the test suite when
  API/test files save; syntax-check saved frontend JS; remind the agent to
  tick `tasks.md` and log design changes after each spec task.
- ✅ **MCP config** (`.kiro/settings/mcp.json`): the `fetch` MCP server is
  configured for Kiro sessions.
- ✅ **Kiro CLI 3.5.0 installed and verified** on the build machine
  (`curl -fsSL https://cli.kiro.dev/install | bash`, glibc 2.39).
- ⚠️ **No authenticated Kiro agent session ran during this build.** Kiro
  sign-in requires an interactive browser/device-flow step that the headless
  build VM cannot complete (details below). **No code in this repo was
  generated by a Kiro agent session.** The `.kiro/` artifacts are genuine
  spec-first artifacts, authored following Kiro's documented formats, and the
  repo is ready for a Kiro session to pick up and continue.

## How the spec-driven workflow shaped the build

1. **Requirements first.** Eight requirements with EARS acceptance criteria
   (`WHEN … THE SYSTEM SHALL …`) were written before a line of code. They
   forced decisions early — e.g. Req 7 (safety) is why the reader endpoint is
   restricted to `web.archive.org`, and Req 2.3 (partial timeline) is why a
   slow archive degrades instead of failing the page.
2. **Design before tasks.** The design doc recorded the architecture (static
   frontend + four zero-dependency functions), the 10s function budget, and
   the CDX→availability-anchor decision with its reason.
3. **Tasks as a checklist.** 15 numbered tasks, each citing its requirements.
   The build worked through them in order; two real changes during the build
   (parallelizing the three resurrect lookups, parallelizing liveness +
   snapshot in `/api/check`) were made to stay inside the 10s limit and are
   logged in the design doc.
4. **Steering as guardrails.** `tech.md` ("zero dependencies", "functions must
   finish in <10s", "validate before you fetch") and `structure.md` (where
   things live, "never gitignore `.kiro/`") were the rules the build was
   checked against.
5. **Hooks as automation.** The two hook files encode the workflows the build
   actually followed by hand: run `npm test` on API/test saves, `node --check`
   on frontend saves, and update the spec after each task. In a Kiro session
   they run automatically.
6. **Property-based testing.** The spec's testing strategy includes
   property-style tests (`tests/property.test.js`, seeded PRNG, 1,000+
   generated cases). They caught two real bugs during the build: a regex that
   treated a stray `"` as an unquoted href, and an IPv6-bracket handling gap
   in the SSRF guard (`[fe80::1]`). Both are fixed and covered by unit tests.

## How to continue this project in Kiro

1. Sign in: `kiro-cli login` (or open the folder in Kiro IDE and sign in).
2. Open this repo. Kiro reads `.kiro/steering/` + `AGENTS.md` automatically.
3. Pick up the spec: `.kiro/specs/revenant/tasks.md` — completed tasks are
   ticked; follow-up ideas (below) can become new specs.
4. Hooks activate automatically: save a file under `api/` or `tests/` and the
   test suite runs; save frontend JS and it is syntax-checked.

Follow-up specs worth writing next: scheduled graveyard audits (re-check a
saved page weekly), a "resurrect this citation" browser bookmarklet, and
per-domain death statistics.
